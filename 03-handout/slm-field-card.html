The decision sequence

answer in order
  1. 01
    What is the task shape? Classification, extraction, routing, format conversion → sub-4B is fine. Tool-calling agent → 7–9B floor. Planning, novel reasoning, cross-repo code → frontier. Task shape decides model size, not the other way round.
  2. 02
    What is N? Count the steps between checkpoints. Above roughly ten unverified steps, decompose before you do anything else. Four verified 5-step segments need p = 0.979 each; one unverified 20-step run needs 0.995.
  3. 03
    What is your volume? Below ~2M tokens/day the engineering cost swamps the token savings. Use a hosted model and revisit when the volume is real.
  4. 04
    Do you have a non-cost reason to self-host? Sovereignty, a latency SLA, per-tenant weights, deprecation risk, air-gap. If not, a cheap hosted small model captures most of the win with none of the ops.
  5. 05
    Do you have a golden set? If not, you cannot answer any of the four questions above with evidence. Build it first: 50–100 cases from real production traffic, 20% deliberately nasty.

Two of these are separate decisions that get conflated constantly. Small vs large is nearly always a win on a narrow task. Self-host vs API is a different question, and it is almost never won on token price.

Budget weights + ~1 GB runtime + KV cache. KV cache is the one everyone forgets — at 64K context it can exceed the weights. Generation speed is memory-bandwidth bound, not compute bound, which is why an M4 barely beats an M2 and loses to an M3 Pro.

Tool support is a property of the chat template, not the parameter count. A 70B with no tool template loses to a 1.7B that has one. Check the model card before you check the leaderboard.

Per-step p required for 90% end-to-end success: N=5 → 0.979  ·  N=10 → 0.990  ·  N=20 → 0.995  ·  N=50 → 0.998. Nothing on any leaderboard is there — small or frontier.

Taken literally this table says nothing works, which is obviously false. The gap between it and production is exactly the engineering: retries, validators, constrained decoding, checkpoints, and short verified segments instead of long unverified ones. Reliability is an engineering outcome, not a model property — one production system took its failure rate from ~14% to 0.4% with no model change at all.

Q2 and below<20%unreliableDon't

Q4_K_M means: 4-bit nominal, K for k-quants (super-blocks of 256, sub-blocks of 32, each with its own quantised scale and min), M for medium mixed precision (attention wv and FFN w2 kept at Q6_K). Net ~4.89 bits per weight — "4-bit" is never four bits, and the overhead is what buys the quality.

Damage is task-dependent, not uniform. Single-shot recall barely moves as you quantise; chained reasoning falls off a cliff. Tool-argument construction and multi-step arithmetic are chained reasoning. And if a QAT checkpoint exists for your model, take it — it cuts the quality drop roughly in half, for free.

Cost

two independent decisions
# the whole self-hosting question in one line
$ per 1M tokens = (GPU $/hr ÷ throughput tok/s) × 1e6 ÷ 3600 ÷ utilisation

Utilisation is the term everyone omits and it swings the answer 5×: same H100, same model — $0.20/1M at full load, $1.01/1M at 20%, $4.03/1M at 5%. Your idle GPU is the biggest line item in a self-hosted quote and it never appears in the vendor's comparison table.

Assumes agent traffic at 80% input / 20% output and a ~$504/month rig. Then add the real total: hardware $1,000 + power and colocation $831 + 25% of one engineer $4,000 ≈ $5,931/month. Staffing is 6–30× the hardware — and that total lands at roughly the price of the hosted API it was meant to beat.

What actually justifies self-hosting: regulation (EU AI Act high-risk obligations took effect 2 August 2026), data sovereignty, a latency SLA where 15s → 0.15s is a different product, per-tenant fine-tuned weights via multi-LoRA, and freedom from silent vendor deprecation. Not token price.

Red flags

reach for a bigger model
  • Horizon beyond ~10 unverified stepsThe compounding math is unforgiving. Decompose or escalate.
  • Broad world knowledge requiredYou cannot fine-tune in facts the model does not have.
  • Code generation across a large repoNeeds long context and long horizon at the same time.
  • Ambiguous or novel reasoningFine-tuning specialises; it does not generalise to the case you did not anticipate.
  • Very long contextDegradation hits everyone, but small models start lower and hit the wall sooner.
  • Low volumeBelow ~2M tokens/day the engineering cost swamps the savings.
  • A single failure is expensiveIrreversible actions, money movement, customer commitments. Even frontier models roughly halve from pass@1 to pass^8.
  • Multilingual breadthCapability concentrates in high-resource languages as parameters shrink.
  • Safety-critical generationNote the asymmetry: small models are excellent at safety classification, weaker at safety alignment under pressure.
  • You have no golden setYou will not be able to tell whether the swap was safe. This is how SLM projects actually die.

Patterns that ship

production-verified
PatternWhat it isEvidence
Cascade Rules → small model → escalate on a validator's verdict, never on the model's self-reported confidence. 1.5M checks/mo: 98% by logistic regression, 2% by a tuned 8B. 80–82% → 90% accuracy, 15s → 0.15s, $12k/mo → <$800.
Heterogeneous SLM for the mechanical high-frequency work; frontier model for planning and error recovery. Agent frameworks estimate 40–70% of calls are replaceable.
Frontier as offline teacher The big model manufactures training data; the small model runs in the hot path and the big one never appears at inference. An 8B edit-prediction model distilled from a frontier teacher: +30% acceptance rate.
Guardrails as SLMs Safety and PII classification is a small-model job. Across 14 guard models 110M–20B: correlation of size with detection r=0.21, p=0.48. A 4B had 3.4× the recall of a 20B.

Evaluation

the part that decides whether it ships
  1. 01
    Score per tag, never just the average. If 90% of your cases are happy-path, your average looks great while every hard case quietly fails.
  2. 02
    Source cases from production failures, not imagination. Instrument for thumbs-down, abandonment and escalation. Triage weekly. Prune cases testing behaviour you deliberately removed.
  3. 03
    Size it honestly. 50–100 cases for one feature. 150–300 for a maturing product. 400+ for a regulated flow. 15–25% deliberately nasty.
  4. 04
    Validate the judge before you trust it. Across 21 judge models, chance-corrected agreement ran 34–41 points below raw agreement — the best scored 84.9% raw but 51.1% kappa. Give it a specific rubric, randomise A/B order, check against ~50 human labels. Several judges were perfectly reproducible while carrying severe position bias: reproducibility is not validity.
  5. 05
    ±1 point on a 200-item set is noise. Quantised models sometimes "beat" fp16 on a benchmark. That is variance, not a discovery.

Tooling: promptfoo for a model bake-off · deepeval for CI gates · lm-evaluation-harness for academic benchmarks only · ragas for RAG.

Model tags move fast — verify the exact tag and file size before you rely on one. Note that a bare tag is often Q8_0, not Q4; ask for -q4_K_M explicitly when size matters.

Converting an existing LLM call

six steps, and the first is the gate
  1. 01
    Log everything Every non-user-facing call: prompt, response, tool calls, latency. Encrypted. Without traces there is no project.
  2. 02
    Curate Strip PII and PHI. Target 10k–100k examples.
  3. 03
    Cluster Unsupervised clustering over prompts and operations. The clusters are your specialisation candidates.
  4. 04
    Select a model Capability, licence, deployment footprint — in that order.
  5. 05
    Fine-tune LoRA or QLoRA, or distil from the model you are replacing.
  6. 06
    Iterate Retrain as usage drifts.
